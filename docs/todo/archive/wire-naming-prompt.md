# Elastic Interface and Wire Naming Prompt

> **Status:** Archived after the naming review. Chext does not enforce an
> `ewire`, `source`, or `sink` vocabulary for interfaces because semantic names
> are common and useful. The resulting guidance is in
> [Naming Conventions](../../naming.md).

We are working in the Scala/Chisel repository `chext`.

## Goal

Review whether Chext should add tracking-time naming diagnostics for Elastic interfaces, especially
interfaces created with `chext.elastic.EWire`. First inspect the repository and discuss a roadmap;
do not implement a naming policy until its expected warnings and migration cost are understood.

## Existing Naming Work

Components and containers have an explicit `namePrefix` contract. Generic tracking checks the most
recent entry of their Chisel prefix stack during `ModuleInfo.onComplete()`. A component name is
accepted when it starts with its expected prefix and the following character is the end of the
name, a digit, an uppercase letter, or an underscore.

Do not assume that the same positive-prefix policy is appropriate for interfaces. Components are
named after what was constructed; interfaces are graph edges and are often named after their
payload, protocol purpose, stage, or role.

## Evidence Collected So Far

A source scan found approximately 130 straightforward `EWire` bindings in Chext main sources:

- 24 start with `ewire`;
- 25 start with `wire`;
- 7 start with `source`;
- 12 start with `sink`;
- 62 use other semantic names.

Examples of existing semantic names include:

- `demuxInput`, `demuxSelect`;
- `queueSink`, `queueSource`;
- `taskAR`, `taskR`, `taskFiltered`;
- `idLast`, `lastRepeated`;
- `stage0_result`;
- container-facing interfaces such as `sinkA`, `sourceResult`, `sinkCurrent`, and `sourceNext`.

Viccup follows a different house style: roughly 124 of 152 `EWire` bindings start with `ewire`.
Allowing `ewire`, `source`, or `sink` as alternative starting prefixes accepts about 150 of those
152 bindings, but only 43 of Chext's 130 bindings.

Names such as the following are considered valid and are an important counterexample to a strict
starts-with rule:

```text
fp32_sourceInA
readAddress
taskInput
resultStream
vertexUpdates
stage1Output
```

Do not create an increasingly complicated token or substring matcher merely to accept these names.
That would still reject good semantic names and could accept unrelated names accidentally.

## Aggregate Distinctions

Chisel binding information can distinguish standalone data from aggregate children:

- standalone wires have a `WireBinding`;
- standalone ports have a `PortBinding` or `SecretPortBinding`;
- members of a `Bundle`, `Record`, `Vec`, or `NamedVec` have a `ChildBinding`;
- DataView-created interfaces can have an `AggregateViewBinding`.

If any interface naming diagnostic is proposed, do not check every child channel independently.
Short aggregate field names such as AXI `ar`, `r`, `aw`, `w`, and `b`, or memory `req` and `resp`,
inherit meaningful context from their enclosing aggregate.

`EWire.many`, `Source.many`, and `Sink.many` return a `NamedVec`. If a policy checks these objects,
check the bound `NamedVec` root once rather than warning for every child interface. Arbitrary
aggregate children should normally be skipped.

## Recommended Direction

Chext should **not enforce vocabulary such as `ewire`, `source`, or `sink` for
interfaces**. Prefer objective diagnostics that do not legislate semantic
naming:

- empty or unusable interface names;
- genuinely anonymous/autogenerated names, if they can be identified reliably;
- duplicate graph paths;
- incorrect Source/Sink use based on tracking roles;
- malformed or unknown interface/view ownership.
